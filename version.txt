1. EXECUTIVE SUMMARY & RESOLUTION LOG
-----------------------------------------------------------------------------
This document tracks all errors, root-cause analyses, and architectural
resolutions implemented during the development and stabilization of the
Voice Typing system.

Initially, the project was split across multiple scripts:
- voice_typing.ahk (AutoHotkey v2 frontend controller and UI overlays)
- voice_transcriber.py (Python backend worker executed as child process)

Due to process lifecycle overhead, Windows hotkey collisions, and multi-runtime
complexity, the architecture was consolidated into an all-in-one native
Python solution (voice_typing_app.py) with translucent Tkinter overlays,
direct keyboard hooks (including Copilot key interception), and direct Gemini
API integration.

* Implementation:

[ERROR 4] Mode 2 (Batch) gemini-3.5-transcribe 400 INVALID_ARGUMENT & Fallback
-----------------------------------------------------------------------------
* Symptoms:
  Mode 2 fell back to gemini-2.5-flash with log:
  "Model gemini-3.5-transcribe failed: 400 INVALID_ARGUMENT"
* Root Cause:
  The code called 'client.models.generate_content(model="gemini-3.5-transcribe")'.
  According to Google Gemini documentation, 'gemini-3.5-transcribe' is designed
  specifically for the new Interactions API, not the legacy generate_content endpoint.
* Resolution:
  Refactored Mode 2 to use the Interactions API:
  - Audio frames are serialized into an in-memory WAV buffer.
  - The WAV is Base64-encoded.
  - Sent via:
      interaction = client.interactions.create(
          model="gemini-3.5-transcribe",
          input=[{"type": "audio", "data": b64_audio, "mime_type": "audio/wav"}]
      )
      transcription = interaction.output_text
  - Verified: Mode 2 transcribes cleanly with gemini-3.5-transcribe with zero fallbacks.

[ERROR 5] Mode 1 (Live) Audio Starvation & 66% Packet Loss
-----------------------------------------------------------------------------
* Symptoms:
  Live session connected successfully, but no speech was transcribed or typed.
* Root Cause:
  Mode 1 was recording audio using:
      audio = sd.rec(1600, samplerate=16000, channels=1, dtype='int16')
      sd.wait()
  in a loop. On Windows (WASAPI/MME), starting and stopping PortAudio audio
  hardware on every 100ms chunk introduced ~200ms of driver spin-up latency per chunk.
  Benchmarking showed:
      Chunk took 0.300s to capture 0.100s of audio!
  This caused 66% of the user's spoken audio to be discarded between chunks.
  The server received fragmented, unintelligible audio syllables.
* Resolution:
  Replaced the polling 'sd.rec()' with a continuous 'sd.InputStream' running in a
  dedicated callback thread, pushing into an 'asyncio.Queue'. The microphone stream
  remains open for the entire duration with 0% dropped audio.

[ERROR 6] Mode 1 (Live) Missing Transcription Config & Response Field Mismatch
-----------------------------------------------------------------------------
* Symptoms:
  Even when connected, live incoming chunks produced no typed text.
* Root Cause (Two parts):
  1) Configuration: Gemini Live API requires 'input_audio_transcription=types.AudioTranscriptionConfig()'
     inside LiveConnectConfig to activate the speech-to-text pipeline.
  2) Response parsing: The script was looking for conversational chatbot turns
     ('response.server_content.model_turn.parts'). The dedicated speech-to-text model
     (gemini-3.5-transcribe-live) returns speech recognition in:
     - 'response.server_content.interim_input_transcription.text' (low-latency live speech)
     - 'response.server_content.input_transcription.text' (finalized phrase)
* Resolution:
  1) Added 'input_audio_transcription=types.AudioTranscriptionConfig()' to LiveConnectConfig.
  2) Implemented real-time response parsing for 'interim_input_transcription' and
     'input_transcription'.
  3) Implemented smooth delta typing: compares the common prefix of what has already
     been typed against the incoming text, sends backspaces for altered punctuation,
     and types incremental words in real-time at the user's cursor.

4. NATIVE KB-SIZED LISTENER ARCHITECTURE (copilot_listener.exe)
-----------------------------------------------------------------------------
* Problem & Design Goal:
  Running a full Python runtime in the background 24/7 wastes 50-80 MB of RAM
  and requires background interpreter threads. The user requested a "KB-sized
  thread, not a full Python, so it just checks whether a specific key is pressed;
  if yes, then launch the script, highly specific."

* Solution Implemented:
  1) Pure C Win32 Daemon (d:\v2c\copilot_listener.c -> copilot_listener.exe):
     - Compiled with GCC: `gcc -O2 -mwindows -s -o copilot_listener.exe copilot_listener.c`
     - Final Executable Size: 19 KB (19,456 bytes).
     - Idle Memory Footprint: ~880 KB RAM (vs ~60 MB for idle Python).
     - CPU Usage: 0.00% (sleeps in Windows kernel GetMessage wait-state).
  2) Dual-Layer Detection Engine:
     - Layer 1: Win32 RegisterHotKey: Registers OS-level hotkeys for Win+Shift+F23,
       Win+F23, F23, VK_F21 (MS Office key), and Ctrl+Shift+H directly with win32k.sys.
     - Layer 2: Win32 Low-Level Keyboard Hook (WH_KEYBOARD_LL): Intercepts raw hardware
       scan codes and suppresses the key so Windows does NOT launch default Copilot.
  3) Session Mutex Handoff:
     - Named Mutex: `Global\VoiceTypingSessionMutex`.
     - When idle: Listener detects Copilot key -> sees mutex is not acquired ->
       spawns `pythonw.exe d:\v2c\voice_typing_app.py` silently.
     - While active: If Copilot key is pressed while Python is already recording,
       the listener passes the key straight to Python so the active session stops,
       outputs the transcription, and exits.
  4) Python Session Auto-Exit:
     - In d:\v2c\voice_typing_app.py, Python runs ONLY for the active transcription session.
     - Mode 1: Stops streaming, finishes typing, and destroys itself (`sys.exit(0)`).
     - Mode 2: Stops recording, transcribes, copies to clipboard, shows confirmation,
       and destroys itself (`sys.exit(0)`).
     - Menu Cancel: If Copilot is pressed or 10s idle, menu destroys itself and exits.
     - Result: 0 MB Python RAM when idle; full resources freed immediately.
